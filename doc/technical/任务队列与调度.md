# 任务队列与调度

版本：v0.1｜更新：2026-10-16｜范围：S05.4公共任务基础，业务处理器按S06以后接入。

## 一、事实与执行边界

PostgreSQL `tasks`／`task_attempts`／`task_inputs`／`task_outputs`保存业务事实；Celery 5.6.3、Kombu 5.6.2与Redis客户端6.4.0由uv.lock锁定。Redis只传组织及Task UUID，不传正文、会话、文件路径或供应商密钥，不启用结果后端。只接受JSON，迟确认、worker丢失重投、prefetch=1；业务重试只走数据库，不调用Celery.retry。

当前唯一正式处理器`file.verify/1`：按真实文件及作品关联检查权限、读取私有存储校验SHA-256与大小，成功生成`file.verified`审计；不是解析、研判报告或正式知识。外部调用预算必须0。未知处理器失败`HANDLER_UNAVAILABLE`；不会自动改用别的来源或模型。

后台以requested_by及execution_authorized_by两名当前成员重检权限和依赖；浏览器会话到期不取消已授权任务，成员禁用／Grant撤回或到期会阻断执行与发布。`MemberPrincipal`仅供可信服务构造，不接受客户端选择执行动作；处理器代码固定动作`content.write`，同时要求作品／文件读取权限。处理器freeze须绑定全部实质输入及版本，返回稳定精确manifest，输入摘要包含处理器版本与两名成员；新增处理器必须实现同样验证，不能把当前文件处理器测试视为所有业务处理器已验收。

## 二、领取、取消、重试与恢复

`queued → running → succeeded/failed`，取消和重试遵循[状态分册](数据字典-权限与状态.md)；任务创建后输入集合即封存。领取前与产物提交前验证当前权限和manifest；发布函数、task_outputs、终态与审计同一事务。匹配活动Attempt、token、Task.lock_version、DB时钟未过期租约才可提交；旧worker失租约或取消先行时不能发布。

默认租约90秒，心跳最多15秒；处理器配合checkpoint，数据库锁等待2秒、单语句5秒；本地文件校验40秒截止，Celery软限50秒、硬限60秒，默认prefork并发2、同组织活动Attempt上限2。硬杀后按租约过期恢复，不宣称Redis ack本身保证执行一次。macOS spawn兼容钩子通过Celery worker_process_init补初始化trace缓存，理由及真实失败证据见执行记录；升级Celery须回归真实子进程。

尝试默认1次，CLI显式允许1～3次。仅LOCAL_TRANSIENT、LEASE_LOST、TIMEOUT可在原上限内自动重试，退避2、4秒（通用函数上限300秒），沿用相同输入／版本／授权成员。任何外部调用预留均阻断本基础层自动重发；中断有调用预留则EXTERNAL_RESULT_UNKNOWN，留待后续供应商核验。INVALID_INPUT、ACCESS_REVOKED、INTERNAL_ERROR、未知处理器不自动重试。不提供加预算／换执行人通道。

Beat每10秒投递`cip.tick`，扫描最多100条到期租约及100条可用queued Task。Task本身是持久待投清单：数据库提交后进程中断、Redis消息丢失或发送失败均可补投；重复消息领取不到第二个活动Attempt。Redis不可用时queued仍保留，下轮调度继续。此调度仅负责已创建Task，不启用来源计划或额外采样，S06另接CollectionPlan。Beat本地schedule文件丢失可重建，不影响Task事实；常规只运行一个Beat，误开多实例仍受数据库幂等约束。

## 三、运行与受控操作

先`pnpm infra check`，`pnpm db:upgrade`，`pnpm db:app-role`。API、worker、Beat使用同一受限APPLICATION_DATABASE_URL、REDIS_URL、TASK_QUEUE、TASK_KEY_PREFIX及STORAGE_ROOT；禁止复用迁移所有者。Redis默认127.0.0.1:16379，仅本地信任边界，远程部署另做网络与认证配置。

两个终端分别启动`pnpm worker`、`pnpm beat`；调度单次维护用`pnpm tasks tick`，只扫描既有任务，不创建样本。下列操作提示输入密码，不把密码或会话放命令行；必须已有受控账号和真实文件，项目不自动开户或填充资料：

```bash
pnpm tasks submit-file --org <组织UUID> --login <登录名> --file <文件UUID> --key <逻辑幂等键>
pnpm tasks status --org <组织UUID> --login <登录名> --task <TaskUUID>
pnpm tasks cancel --org <组织UUID> --login <登录名> --task <TaskUUID> --expected <lock_version>
pnpm tasks retry --org <组织UUID> --login <登录名> --task <TaskUUID> --expected <lock_version>
```

submit默认只尝试一次，可显式`--max-attempts 2`；重试不能增加上限，未知效果不能绕过。状态查询仅返回task.read允许的安全字段，不能看到输入输出正文。CLI所有写动作均有审计，临时登录最终退出。

## 四、增量数据库契约与验证

迁移`0007_tasks`不新增表／字段，保留74表。新增固定search_path、SECURITY DEFINER的`cip_task_control(uuid,uuid,bigint,text,uuid,uuid,integer,text) → boolean`：按组织锁与expected_lock_version控制renew／fail_queued／cancel／retry／recover，续租还检token、Attempt和DB时间；权限仅授受限应用角色，PUBLIC不可执行。重试在SQL再检安全错误、尝试上限、无活动Attempt及无外部调用，不能仅靠Python判断。应用角色仍不可直接更新Task.state或Attempt；此函数与现有claim/finish一样是可信服务的数据库入口，不代替成员权限。

升级应用前先迁移再刷新应用角色授权；旧worker应先停止，避免新旧执行策略混跑。降级0007仅移除控制函数，需先停止worker／Beat并核查无活动任务；Task和审计仍保留，不删除历史。既有0001～0006 SQL校验和不改。

验证命令：`pnpm db:test`（随机库、真实Redis随机前缀、临时文件、独立worker／Beat与SIGKILL恢复），`bash scripts/check.sh`（工程检查）。不使用eager模式；测试只清理自身命名空间，不FLUSH Redis、不清业务库。执行进度和最终证据见[S05.4记录](../plans/2026-10-16-S05.4任务队列与调度.md)。

依据：[Celery任务与迟确认](https://docs.celeryq.dev/en/stable/userguide/tasks.html)、[周期调度](https://docs.celeryq.dev/en/stable/userguide/periodic-tasks.html)、[Redis重投语义](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html)。这些机制提供传输与调度，应用幂等仍由数据库验证。

已知轻微限制：CLI `submit-file`同键回放既有终态Task时仍固定打印`state=queued`，实际不会重跑，当前以`status`结果为准；此提示问题已登记待改，不影响数据库状态与幂等。手动重试审计记录当前task.manage操作者，自动重试记录当前执行授权上下文，二者不混记。
